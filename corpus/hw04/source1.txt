                Designing a REST API
●   Model resources as nouns, not actions
    ○   Good: GET /students/42/courses
    ○   Avoid: GET /getStudentCourses?id=42
● The method is the verb. The path is the thing.
● Practical rules

    ○   Plural collection names: /students, /courses
    ○   Version the API: /v1/students
    ○   Paginate every list endpoint: ?limit=50&offset=100
    ○   Return errors in a consistent JSON shape, never a raw stack
        trace
    ○   Filter and sort with query parameters, not new endpoints
●   Document the contract with OpenAPI. FastAPI
    generates it for you at /docs - one of the reasons we
    use it in this course.

    Why Kafka? Synchronous vs Event-Driven
●   Synchronous (REST): the caller waits for the reply
     ○ Simple to reason about, easy to debug
     ○ But the caller is blocked, and if the callee is down the
       request fails
●   Asynchronous (Kafka): the producer writes an event
    and moves on
     ○ Consumers read the event when they are ready
     ○ Producer and consumer need not be running at the
       same time
●   Use it when work is slow, retryable, or must fan out
    to several services. Do not use it when the user is
    waiting for the answer.

     AI Agents: What is an Agent?
An Agent is a system designed to achieve goals through an iterative cycle of reasoning and
interaction with its environment.

Core Process
1.    Plan → Formulate actions toward a goal.
2.    Act → Execute actions, often by using external tools or functions.
3.    Observe → Perceive feedback or results from the environment.
4.    Reflect → Update internal state and strategy based on outcomes.

This loop repeats until the goal is reached (or the task terminates).

Key Components
 ●    LLM “Brain” – Provides reasoning, planning, and language understanding.
 ●    Tools / Function Calls – Extend capabilities (e.g., search, API calls, computation).
 ●    Memory / State – Stores context, history, and learned knowledge for continuity.
 ●    Control Loop – Governs the cycle of planning, acting, observing, and reflecting.

 Tools and functions (schemas matter)
● Tools are typed functions (name, inputs, outputs) exposed to the
  model
  Name – identiﬁer for the model (e.g., search_web)
  Inputs – required arguments (e.g., {query: string})
  Outputs – expected return values (e.g., {results: list of strings})
● Clear contracts ⇒ higher reliability, safer actions, easier
  Example: A calculator tool guarantees numeric inputs/outputs
  only.
● Start with a small allowlist and expand deliberately
  Example: Begin with “search” + “summarize,” later add “email” or
  “database query.”
● Schemas: JSON or YAML deﬁnitions that describe tool capabilities
                   {

                       "inputs": { "expression": "string" },

Tool use — Agents invoke external functions with strict schemas.
Example:
 ●   Tool: weather_lookup({location: "San Jose"})

Plan: (1) Search flights → (2) Compare prices → (3) Book hotel → (4) Build itinerary.

Reﬂection — Model self-critiques outputs and retries when errors occur.

Memory that matters
Short-term: Keeps track of the last few turns of context, Example:
ConversationBufferWindowMemory(k=6) → model “remembers” the last 6
exchanges. Useful for: chit-chat, short tasks, avoiding overload.
Episodic: Stores summarized chunks of past interactions. Example:
ConversationSummaryMemory → auto-generates summaries of earlier sessions.
Useful for: keeping track of multi-session progress without recalling every detail.
Long-term: Uses vector databases to store and retrieve knowledge over time.
Example: FAISS + HuggingFaceEmbeddings + retriever/tool → semantic
search across prior conversations, documents, or knowledge base. Useful for:
recalling facts, prior work, personal history.
Forgetting: Windowed memory (k) → discards oldest turns. Episodic TTL (time-to-live) →
optional expiration of memories after set time. Useful for: controlling memory growth, ensuring
relevance.
Example in action:

 ●   User: “Remind me what we discussed about robotics last week.”
 ●   Short-term memory → no record.
 ●   Episodic memory → summary: “User explored simulation platforms.”
 ●   Long-term memory → retrieves FAISS entry with exact notes: “We used Habitat and iGibson for
     navigation tasks.”

              Evaluating an Agent
● Non-deterministic systems cannot be tested
  with assertEqual alone
● What to measure
    ○ Task success rate - did it finish the job, judged
      against a fixed set of cases
    ○ Steps per task - a rising step count usually means

      confusion
    ○ Tool-call accuracy - right tool, right arguments

    ○ Cost per task - tokens x price, summed over every

      loop iteration
    ○ Latency, p50 and p95 - agents are slow, and users

      notice the tail
              Evaluating an Agent
●   Practical habits
    ○ Build a small evaluation set early: 20 to 50 realistic
      tasks
    ○ Log every step - prompt, tool call, observation,

      decision
    ○ Always compare against a simpler baseline (single

      prompt, or RAG)
●   If the agent does not beat the baseline, ship the
    baseline.

Use AI to Learn, Not to Replace Learning
Hands-On Coding Builds Real Understanding
 ● AI can generate code quickly, but reading generated code is not the
   same as knowing how to build it
 ● Writing, running, debugging, and modifying code yourself develops the
   technical foundation needed to understand how a system actually works
Do Not Turn Homework Into Copy-and-Paste
 ● Do not copy the homework prompt into ChatGPT and submit the
   generated answer as your own work
 ● If you cannot explain your code or reproduce the results yourself, you
   have not completed the learning objective
Productive Struggle Is Part of Learning
 ● Debugging errors, interpreting unexpected results, and figuring out why
   something failed are essential parts of becoming a strong developer
 ● Letting AI bypass every difficult step weakens independent
   problem-solving skills
 ● Hands-on practice builds the judgment needed to recognize when
   AI-generated code is wrong, inefficient, or inappropriate
              Course Policy using AI-assisted Coding

AI-assisted coding (“vibe coding”) can be a powerful tool, but it should
support—not replace—the development of fundamental programming
skills.

● Build the foundation first. Do not rely on AI-assisted coding until you have
  implemented, run, and debugged similar programs manually several times.
● Homework emphasizes hands-on coding. Homework assignments and
  pair-programming activities are designed to strengthen your own coding,
  debugging, and problem-solving skills (No AI Coding)
● AI-assisted coding is allowed for the group project. Once foundational
  skills have been developed, you may use AI tools more extensively to
  accelerate development, explore alternatives, and integrate larger systems.
● You remain responsible for the code. Whether code is written manually or
  generated with AI, you must be able to explain, test, modify, and debug it.

Ultimately, the key lies in learning to harness AI
● Boost productivity by automating repetitive tasks.
● Enable innovative solutions previously unattainable.

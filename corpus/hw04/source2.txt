Where regular functions are safer

and you do not need your own this, arguments, or constructor
behavior. Use traditional function syntax when those behaviors
matter.

                  HTTP: https://en.wikipedia.org/wiki/HTTP
HTTP stands for "Hypertext Transfer Protocol" and is the primary protocol used
to transfer data across the web, essentially deﬁning the rules for how web
browsers and servers communicate with each other to display web pages and
access online content.
  • Client-server model:
     HTTP operates on a client-server model where a client (like a web browser)
     sends a request to a server, which then responds with the requested data.
  • Stateless protocol:
     each request is independent, Messages have headers + optional body
     Status codes communicate outcome (2xx/4xx/5xx)
  • Data transfer:
     HTTP is used to transfer various types of data like text, images, videos,
     and application data.
  • Request-response cycle:
     The basic interaction involves a client
     sending an HTTP request to a server,
     which then sends an HTTP response
     containing the requested data.

 Multiple Representation Formats:
 Server must return the data in more than one format (XML, JSON etc).

 For client to specify what format the server should reply, ACCEPT http
 request header needs to be set. Ex. ACCEPT : Application/xml.

 For server to specify what format is being used in the response format,
 Content-Type http response header needs to be set.
 Ex. Content-Type : Application/xml.

FastAPI Dependency Injection (DI)
What it is: A way to declare what an endpoint needs (auth, DB session, config, shared
params) and have FastAPI automatically provide it per request.
 ● How it works: Use Depends() to “inject” the return value of a dependency
    function into your path operation.
 ● Why it matters:
     ○ Reusable logic (auth, DB, validation) across routes
     ○ Cleaner endpoints (separate concerns)
     ○ Testable (override dependencies in tests)
     ○ Supports dependency graphs (dependencies can depend on other
         dependencies)

●   Cleanup support: Dependencies can use yield for setup + teardown (e.g.,
    open/close DB session).
●   Two common patterns:

     ○   Inject as a parameter: user = Depends(get_current_user)
     ○   Run as a route requirement:
         dependencies=[Depends(require_admin)]                                   42

  What "agentic" really means
Simple idea: a loop of
Plan → Do → Check → Adjust/Act (think PDCA).
It’s a continuous improvement cycle first developed by W. Edwards Deming, widely
used in engineering, management, learning, and problem-solving.
 ● Plan – Decide what you want to do and how.
 ● Do – Execute the plan (try it out).
 ● Check – Review the results (did it work as expected?).
 ● Adjust (or Act) – Make changes to improve, then repeat.


Example: Article Summarization
 ● Plan: Outline key points you want in the summary.
 ● Do: Fetch and summarize the article.
 ● Check: Is the summary concise and accurate?
 ● Adjust: Shorten text, add references.
    → Repeat loop until the summary is sharp.

A2A — what is Agent-to-Agent?


Agents message each other to solve tasks, sometimes with a
supervisor or a group chat manager deciding who speaks next.

A2A = agents collaborating like a team.
They pass messages, share results, and build on each other’s
work.
MCP vs A2A — two protocols, two jobs
MCP (Model Context Protocol) — how an agent reaches its tools and data
●   An open standard for exposing tools, resources and prompts to an LLM app.
●   The agent asks a server: what can I call, and how? One agent, many capabilities.
●   Your FastAPI service is exactly this surface — typed inputs, validated bodies,
     ● an OpenAPI schema the model can read before it calls anything.

A2A (Agent-to-Agent) — how an agent reaches its peers
●   A protocol for agents to advertise skills, delegate a task and return a result.
●   The agent asks another agent: can you take this? Many agents, one goal.
●   The ping-pong and supervisor patterns on the next slides are A2A.

They compose, they do not compete
●   A single agent typically uses MCP downward to its tools and A2A sideways
     ● to its peers — the supervisor delegates over A2A, each worker calls tools over MCP.
●   Rule of thumb: MCP answers "what can I use?" — A2A answers "who can help me?"
A2A — ping-pong (to & fro context passing)
What Happens:
1. Agent A → sends a message with context.
2. Agent B → replies, adds reasoning or output.
3. The chat history/summary is shared back so both agents see the updated
     state.
4. Repeat this back-and-forth until a stop rule is met (e.g., task complete or max
     turns).
Example: Debugging a Function
 ● Agent A (Coder): “Here’s the function, but it throws an error.”
 ● Agent B (Reviewer): “The issue is a missing import. Add import os.”
 ● Agent A: Updates code, posts new version.
 ● Agent B: Runs tests again, confirms fix.
 ● Stop when Reviewer approves
Key Idea
Ping-pong = agents pass context back and forth, each improving or correcting,
until the goal is reached.
Minimal Example
A2A Ping-Pong (Fibonacci Task) : Goal: “Write Python to compute the 10th
Fibonacci number.”

Turn 1 — Analyst (A): “Plan: Use recursion or iteration. Keep it simple with a loop.”
→ Sends plan to Coder (B).
Turn 2 — Coder (B): “Wrote a loop version. Code runs but missing print statement.”
→ Returns code sketch + status.
Turn 3 — Analyst (A): “Context summary: last turn = loop works, missing print.
TODO: add print.” → Suggests fix.
Turn 4 — Coder (B): “Updated code. Now prints the 10th Fibonacci number = 55.”
→ Reports success.
Carry Context Each Turn: Summarize what changed + open TODOs → keeps loop
efficient.
Stop Rule:
 ● End when Coder outputs final working code
 ● Or max 6 turns to prevent infinite ping-pong.

Ping-Pong A2A = goal → back-and-forth refinement → stop when done.
A2A with graphs — LangGraph supervisor
pattern
 ●   Agents are graph nodes (Planner, Researcher, Coder, Reviewer).
 ●   A Supervisor LLM is a routing node: it reads current state and decides the next node.
 ●   Edges encode possible next hops; the graph executes step-by-step until a stop rule.


What state does the next agent see?
You choose the state model. Two common patterns:
1) Pass messages (chat-style state) State: messages[] (running conversation) + optional
scratchpad.
 ● Next agent sees: the latest summarized transcript (or last N turns) plus any role tags.
 ● Pros: Natural, debuggable, model-agnostic.

 ●   Task finished? Stop rule met (status=done, artifact produced, tests pass)
 ●   Tool errors? Rate, types, retries, backoffs
 ●   Loops avoided? Max turns not exceeded; no oscillation (A↔B→A↔B with no state change)
 ●   Latency & cost: per-agent, per-tool, per-episode budgets

repeatable tests)
 ●   check: pass ﬁxtures through each role?
 ●   Planner: given a goal fixture, returns ordered steps with acceptance criteria
 ●   Researcher: given a query fixture, returns sources + citations (schema-validated)
 ●   Coder: given a spec fixture, returns runnable code + tests
